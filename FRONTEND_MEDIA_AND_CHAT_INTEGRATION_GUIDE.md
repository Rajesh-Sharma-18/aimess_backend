## 1. Introduction

AIMess is a microservice backend fronted by a single **API Gateway**. The frontend talks to exactly two surfaces:

| Surface       | Base                                                                            | Purpose                                                                                                         |
| ------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **REST**      | `https://<gateway-host>/api/v1`                                                 | Auth, profiles, communities, **media URL issuance**, **chat history**, pins, reactions, forwards, search.       |
| **Socket.IO** | `wss://<gateway-host>/socket.io/` (namespaces `/chat`, `/community`, `/notify`) | Real‑time message send/receive, typing, read/delivery receipts, reactions, presence, calls, live notifications. |

> Production socket origin: `wss://aimess.api.vasundharasolutions.com/socket.io/`.

### How media works (object‑key model)

Media **never travels through the gateway or the socket**. The flow is always:

1. Ask the backend for a **presigned upload URL** (`POST /api/v1/media/upload-url`). You get back a one‑time `uploadUrl`, a permanent `objectKey`, and a ready‑to‑use `media.downloadUrl`.
2. **PUT** the raw file bytes directly to `uploadUrl` (straight to MinIO/S3 object storage).
3. Reference the file in a message by its **`objectKey`** (never by a URL).
4. On every read (chat history, socket broadcast), the backend **resolves the object key into a fresh presigned `url`** — "resolve‑on‑read". You render that `url`.

**Golden rule:** The database only ever stores the **raw `objectKey`**. Presigned URLs are short‑lived and generated on the fly. The frontend **stores the `objectKey`** and **displays the `url`/`downloadUrl`**.

### How chat works

There are **three conversation domains**, all served by `chat-service` and proxied under `/api/v1/chat/...`:

| Domain               | What it is                      | REST prefix                  | Socket namespace |
| -------------------- | ------------------------------- | ---------------------------- | ---------------- |
| **Private (direct)** | 1‑to‑1 DMs                      | `/api/v1/chat/private/...`   | `/chat`          |
| **Group**            | Closed multi‑member group chats | `/api/v1/chat/groups/...`    | `/chat`          |
| **Community**        | Open, joinable public rooms     | `/api/v1/chat/community/...` | `/community`     |

- **Private and Group** share one Socket.IO namespace (`/chat`) and one canonical message shape. The send event carries `conversationType: "private" | "group"`.
- **Community** is a separate namespace (`/community`) with its own (flatter) message shape.

### How sockets work

- One Socket.IO connection per namespace, authenticated with your JWT in the handshake.
- You **send** a message via a client→server event (e.g. `message:send`) and get an **acknowledgement** callback with the server‑assigned `messageId` and `sequenceNumber`.
- The server **broadcasts** the canonical message to everyone in the room (e.g. `message:new`), including a copy back to the sender's other devices.
- Rooms are **server‑computed** (`conv:<id>`, `community:<id>`, `user:<id>`). You never name a raw room; you join via `conv:join` / `community:join`.

### What the frontend must store vs. receive

| You **store** locally                    | You **receive** from backend                  | You **never** persist        |
| ---------------------------------------- | --------------------------------------------- | ---------------------------- |
| `objectKey` (for every uploaded file)    | presigned `url` / `downloadUrl` (render only) | presigned URLs (they expire) |
| `messageId` / `id` (server id)           | `sequenceNumber` (ordering & gap‑fill)        | `uploadUrl`                  |
| `clientMessageId` (your idempotency key) | `serverTs` (authoritative timestamp)          | manually built media URLs    |
| highest `sequenceNumber` per room        | full canonical message on `message:new`       | —                            |

## 2. Quick Start

### Send an image in a private chat (end‑to‑end)

```js
// ── 0. One‑time: connect the /chat socket ───────────────────────────────
import { io } from "socket.io-client";
const chat = io("wss://aimess.api.vasundharasolutions.com/chat", {
  path: "/socket.io/",
  auth: { token: accessToken }, // JWT — see §3
  transports: ["websocket"],
});

// ── 1. Get an upload URL ────────────────────────────────────────────────
const up = await fetch("https://<gw>/api/v1/media/upload-url", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    Authorization: `Bearer ${accessToken}`,
  },
  body: JSON.stringify({
    category: "CHAT_ATTACHMENT",
    contentType: "image/jpeg",
    contentLength: file.size,
  }),
}).then((r) => r.json());

const { uploadUrl, objectKey, headers, media } = up.data;

// ── 2. Upload the bytes straight to storage (NOT through the gateway) ────
await fetch(uploadUrl, {
  method: "PUT",
  headers, // { "Content-Type": "image/jpeg" } — required
  body: file,
});

// ── 3. Join the conversation room (once) and send the message ───────────
chat.emit("conv:join", { conversationId });

chat.emit(
  "message:send",
  {
    conversationId,
    clientMessageId: crypto.randomUUID(), // idempotency key
    conversationType: "private",
    contentType: "IMAGE",
    contentText: "Check this out!",
    files: [
      {
        objectKey, // ← reference the key, never the URL
        name: file.name,
        size: file.size,
        mime: "image/jpeg",
        width: 1920,
        height: 1080,
        blurhash: "UHX}YQ_J...", // optional instant‑preview
      },
    ],
  },
  (ack) => {
    // ── 4. Acknowledgement ────────────────────────────────────────────────
    if (ack.success) {
      console.log("sent", ack.data.messageId, "seq", ack.data.sequenceNumber);
    } else {
      console.warn("failed", ack.error, "retryable?", ack.retryable);
    }
  }
);

// ── 5. Render media — peers (and your other devices) receive: ───────────
chat.on("message:new", (msg) => {
  // msg.content.files[0].url is a ready presigned URL — render it directly
  renderImage(msg.content.files[0].url);
});
```

That is the entire loop: **upload URL → PUT bytes → socket send → ack → render the resolved `url`**. Every media type (video, voice, document) follows the identical shape — only `contentType`, `mime`, and the optional metadata fields (`durationMs`, `waveform`, …) change.

## 3. Authentication Requirements

### 3.1 REST APIs

Every protected endpoint requires a **Bearer access token** (JWT) issued by `auth-service`.

| Header          | Required    | Value                  | Notes                                                            |
| --------------- | ----------- | ---------------------- | ---------------------------------------------------------------- |
| `Authorization` | ✅          | `Bearer <accessToken>` | Validated by `@aimess/auth-jwt`. 401 if missing/expired/invalid. |
| `Content-Type`  | ✅ (writes) | `application/json`     | For all JSON request bodies.                                     |
| `x-lang`        | optional    | e.g. `en`, `hi`        | Localizes server messages. Falls back to `Accept-Language`.      |

```http
POST /api/v1/media/upload-url HTTP/1.1
Host: aimess.api.vasundharasolutions.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6...
Content-Type: application/json
x-lang: en
```

**401 shape** (auth failures are plain objects, not the success envelope):

```json
{ "success": false, "message": "Authentication required" }
```

### 3.2 Socket.IO

| Aspect                      | Value                                                                              |
| --------------------------- | ---------------------------------------------------------------------------------- |
| **URL**                     | `wss://<gateway-host>` + namespace (`/chat`, `/community`, `/notify`)              |
| **Path**                    | `/socket.io/`                                                                      |
| **Auth method**             | JWT passed in the **handshake**                                                    |
| **Token field (preferred)** | `socket.handshake.auth.token` → client `io(url, { auth: { token } })`              |
| **Token field (fallback)**  | `Authorization: Bearer <token>` header                                             |
| **Locale**                  | `x-lang` or `Accept-Language` header at handshake → drives localized ack `message` |

After a successful handshake the server attaches to `socket.data`: `userId`, `sessionId`, `locale`, `tokenExpiresAt`, `accessToken`. Connection is **rejected** with `Error("Authentication required")` / `Error("Authentication failed")` if the token is missing or invalid.

```js
const chat = io("wss://<gw>/chat", {
  path: "/socket.io/",
  auth: { token },
  transports: ["websocket"],
});
const community = io("wss://<gw>/community", {
  path: "/socket.io/",
  auth: { token },
  transports: ["websocket"],
});
const notify = io("wss://<gw>/notify", {
  path: "/socket.io/",
  auth: { token },
  transports: ["websocket"],
});
```

**Token lifecycle on the socket.** The server warns the client ~5 min before the access token expires via a `session:expired` event `{ reason:"TOKEN_EXPIRED", expiresAt, reconnect:true, gracePeriod:60 }`, then force‑disconnects after a 60s grace window. You can refresh **without reconnecting the transport** by emitting `auth:refresh { refreshToken }` (ack returns success). Otherwise, reconnect with a fresh access token.

## 4. Complete Media Upload Flow

All media URL issuance is centralized in **`media-service`**, proxied at `/api/v1/media`. There is also a backward‑compatible avatar alias at `/api/v1/users/uploads/url`.

> **Runtime note:** Files are PUT **directly to object storage** using the presigned `uploadUrl`. The gateway/socket are never in the file path. The presigned PUT signs only the `Content-Type` header — you must send exactly the `headers` object returned to you.

### 4.1 `POST /api/v1/media/upload-url`

**Purpose:** Issue a one‑time presigned PUT URL + a permanent object key for a file you are about to upload.

**Authentication:** `Authorization: Bearer <jwt>` (required). Rate limit: **200 requests / 15 min** per user.

**Request payload**

| Field           | Type          | Required | Rules                                                                                      |
| --------------- | ------------- | -------- | ------------------------------------------------------------------------------------------ |
| `category`      | enum          | ✅       | One of the 7 categories below.                                                             |
| `contentType`   | string        | ✅       | 1–128 chars; **must be allowed for the category** (else 415).                              |
| `contentLength` | number        | ✅       | Bytes; `≥ 1` and `≤ maxBytes` for the category (else 400).                                 |
| `ownerId`       | string (UUID) | optional | Defaults to the caller's `userId`. For `COMMUNITY_*`/`GROUP_*` set the community/group id. |

**Categories, limits & allowed MIME types**

| `category`                  | Key prefix               | Max size | Allowed `contentType`                            |
| --------------------------- | ------------------------ | -------- | ------------------------------------------------ |
| `USER_AVATAR`               | `avatars`                | 5 MB     | `image/jpeg`, `image/png`, `image/webp`          |
| `GROUP_AVATAR`              | `group-avatars`          | 5 MB     | `image/jpeg`, `image/png`, `image/webp`          |
| `COMMUNITY_AVATAR`          | `community/avatar`       | 5 MB     | `image/jpeg`, `image/png`, `image/webp`          |
| `COMMUNITY_COVER`           | `community/cover`        | 5 MB     | `image/jpeg`, `image/png`, `image/webp`          |
| `CHAT_ATTACHMENT`           | `chat-uploads`           | 100 MB   | image + video + audio + docs (see chat MIME set) |
| `GROUP_CHAT_ATTACHMENT`     | `group-chat-uploads`     | 100 MB   | image + video + audio + docs                     |
| `COMMUNITY_CHAT_ATTACHMENT` | `community-chat-uploads` | 100 MB   | image + video + audio + docs                     |

**Chat MIME set** (for the three `*_CHAT_ATTACHMENT` categories):
`image/jpeg`, `image/png`, `image/webp`, `image/gif`, `video/mp4`, `video/quicktime`, `audio/mpeg`, `audio/ogg`, `audio/wav`, `application/pdf`, `application/msword`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`.

**Request example**

```json
{
  "category": "CHAT_ATTACHMENT",
  "contentType": "image/jpeg",
  "contentLength": 204800
}
```

**Response payload** (`200`)

| Field                  | Type          | Description                                                                     |
| ---------------------- | ------------- | ------------------------------------------------------------------------------- |
| `data.uploadUrl`       | string        | Presigned **PUT** URL. Expires in `uploadExpiresIn` s (default **900**).        |
| `data.objectKey`       | string        | `{prefix}/{ownerId}/{fileId}.{ext}` — **store this**.                           |
| `data.uploadExpiresIn` | number        | Seconds until `uploadUrl` expires.                                              |
| `data.maxBytes`        | number        | Size ceiling for the category.                                                  |
| `data.headers`         | object        | Headers you **must** send on the PUT (e.g. `{ "Content-Type": "image/jpeg" }`). |
| `data.media`           | `MediaObject` | Full descriptor incl. a ready `downloadUrl` (valid once the PUT lands).         |

**Response example**

```json
{
  "success": true,
  "message": "Upload URL created.",
  "data": {
    "uploadUrl": "https://minio.example.com/chat-uploads/9f.../a1b2c3d4.jpg?X-Amz-Algorithm=...",
    "objectKey": "chat-uploads/9f8e7d6c-.../a1b2c3d4.jpg",
    "uploadExpiresIn": 900,
    "maxBytes": 104857600,
    "headers": { "Content-Type": "image/jpeg" },
    "media": {
      "fileId": "a1b2c3d4",
      "objectKey": "chat-uploads/9f8e7d6c-.../a1b2c3d4.jpg",
      "fileName": null,
      "contentType": "image/jpeg",
      "size": null,
      "downloadUrl": "https://minio.example.com/chat-uploads/.../a1b2c3d4.jpg?X-Amz-Expires=3600&...",
      "downloadUrlExpiresIn": 3600,
      "uploadUrl": "https://minio.example.com/.../a1b2c3d4.jpg?X-Amz-Expires=900&...",
      "uploadUrlExpiresIn": 900,
      "uploadHeaders": { "Content-Type": "image/jpeg" }
    }
  }
}
```

**Validation rules**

- `contentType` must be in the category's allow‑list → **415** otherwise.
- `contentLength` in `[1, maxBytes]` → **400** (`UPLOAD_FILE_EMPTY` / `UPLOAD_FILE_TOO_LARGE`) otherwise.
- Unknown `category` → **400** (`MEDIA_UNKNOWN_CATEGORY`).

**Error responses**

| Status | When                                            | Body                                                                            |
| ------ | ----------------------------------------------- | ------------------------------------------------------------------------------- |
| 400    | bad body / empty / too large / unknown category | `{ "success": false, "message": "..." }`                                        |
| 401    | missing/invalid JWT                             | `{ "success": false, "message": "..." }`                                        |
| 415    | content type not allowed for category           | `{ "success": false, "message": "..." }`                                        |
| 429    | > 200 requests / 15 min                         | `{ "success": false, "message": "Too many requests, please try again later." }` |

### 4.2 Upload the bytes (PUT to storage)

```js
await fetch(uploadUrl, { method: "PUT", headers, body: fileBlob });
// `headers` MUST be the object from the response (signed Content-Type).
// On success the object is durably stored under `objectKey`.
```

- No `Authorization` header on this request — the URL itself is the credential.
- Do **not** add extra headers; only `Content-Type` is signed.

### 4.3 `POST /api/v1/media/download-url`

**Purpose:** Mint a fresh presigned **GET** URL for an existing object (e.g. to re‑open an attachment after the original presigned URL expired). Most reads do **not** need this — chat history and socket broadcasts already embed resolved URLs.

**Auth:** Bearer (required). Rate limit: 200 / 15 min.

**Request**

```json
{
  "objectKey": "chat-uploads/9f8e7d6c-.../a1b2c3d4.jpg",
  "category": "CHAT_ATTACHMENT"
}
```

**Authorization rules**

- `CHAT_ATTACHMENT`: key must be owned by the caller (`{prefix}/{callerId}/...`) → else **403**.
- `COMMUNITY_CHAT_ATTACHMENT` / `GROUP_CHAT_ATTACHMENT`: prefix‑only check → **400** on mismatch.
- Avatars / covers: any authenticated user may request.

**Response** (`200`)

```json
{
  "success": true,
  "message": "Download URL created.",
  "data": {
    "downloadUrl": "https://minio.example.com/chat-uploads/.../a1b2c3d4.jpg?X-Amz-Expires=3600&...",
    "downloadUrlExpiresIn": 3600,
    "media": { "...": "MediaObject (uploadUrl/uploadUrlExpiresIn null)" }
  }
}
```

**Errors:** 400 (`MEDIA_INVALID_OBJECT_KEY`/invalid), 401, 403 (`CHAT_MEDIA_FORBIDDEN`), 429.

### 4.4 `DELETE /api/v1/media/uploads/:objectKey?category=...`

**Purpose:** Cancel/clean up an upload (delete the stored object). Useful if the user aborts after the PUT.

**Auth:** Bearer (required). **Owner‑only** — key must be `{prefix}/{callerId}/...`.

- `:objectKey` must be **URL‑encoded** (it contains `/`).
- `category` is a query param.

```http
DELETE /api/v1/media/uploads/chat-uploads%2F9f8e..%2Fa1b2c3d4.jpg?category=CHAT_ATTACHMENT
Authorization: Bearer <jwt>
```

**Response:** `{ "success": true, "message": "Upload cancelled", "data": null }`
**Errors:** 400 (validation / unknown category), 401, 403 (`MEDIA_CANCEL_FORBIDDEN`), 429.

> ⚠️ **Not in Swagger.** This endpoint exists and works but is **undocumented** in the OpenAPI spec (see §16).

### 4.5 Legacy avatar alias — `POST /api/v1/users/uploads/url`

A thin, fully‑supported gateway adapter for older clients. It only does **user avatars**.

**Request**

```json
{ "type": "AVATAR", "contentType": "image/jpeg", "contentLength": 204800 }
```

- `type` **must** be the literal `"AVATAR"` → else **400** `{ "success": false, "message": "Invalid upload type. Only \"AVATAR\" is supported." }`.
- Internally renamed to `category: "USER_AVATAR"` and forwarded to `media-service`. Response is the **same shape** as §4.1.
- **503** if `media-service` is unreachable.

> New clients should use `POST /api/v1/media/upload-url` with `category: "USER_AVATAR"` directly.

## 5. End‑to‑End Upload Flow

```
 Frontend
    │
    │ 1. POST /api/v1/media/upload-url  { category, contentType, contentLength }
    ▼
 API Gateway ──▶ media-service ──▶ generates presigned PUT + objectKey
    │
    │ 2. ◀── { uploadUrl, objectKey, headers, media:{ downloadUrl } }
    ▼
 Frontend  ── store objectKey ──┐
    │                           │
    │ 3. PUT <uploadUrl> (bytes, Content-Type header)
    ▼                           │
 MinIO / Object Storage  ◀──────┘   (file lands at objectKey)
    │
    │ 4. socket message:send { conversationId, contentType, files:[{ objectKey }] }
    ▼
 /chat namespace ──▶ chat-service: persist message (stores raw objectKey)
    │
    │ 5. ack { success, data:{ messageId, sequenceNumber, sentAt } }
    ▼
 Frontend (sender)                     ┌─ message:new (resolved url) ─▶ Receiver
    │                                   │
 chat-service ── publish Redis ─────────┤
    │                                   └─ message:new (resolved url) ─▶ Sender's other devices
    │
    │ 6. Chat history GET returns content.files[].url  (presigned, resolve-on-read)
    ▼
 Frontend renders media from `url`
```

**Key invariants**

- The DB persists only `objectKey`. Step 6 (and the step‑5 broadcast) re‑sign a **fresh `url`** every read.
- `message:new` is delivered to the **sender too** (multi‑device), so optimistic UIs should reconcile by `clientMessageId`.

## 6. Chat Message Flow

This section covers **private & group** messages (namespace `/chat`, canonical shape). Community is in **§8**.

All media messages share one envelope; only `contentType` and the per‑file metadata differ. The send event is `message:send`; the broadcast is `message:new`.

### `message:send` payload (shared)

| Field                        | Type                     | Notes                                                                                                          |
| ---------------------------- | ------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `conversationId`             | string                   | Required. The room id.                                                                                         |
| `clientMessageId`            | string                   | Your idempotency key (UUID). Echoed back; dedupes retries.                                                     |
| `conversationType`           | `"private"` \| `"group"` | Default `"private"` (case‑insensitive).                                                                        |
| `contentType`                | string (UPPER)           | `TEXT`/`IMAGE`/`VIDEO`/`VOICE`/`AUDIO`/`DOCUMENT`/`GIF`/`STICKER`/`LOCATION`/`CONTACT`. Auto‑uppercased.       |
| `contentText`                | string                   | ≤ 4000 chars. The caption / body.                                                                              |
| `files[]`                    | array                    | ≤ 30. Each: `{ objectKey?, url?, name?, size?, mime?, width?, height?, durationMs?, blurhash?, waveform?[] }`. |
| `urls[]`                     | string[]                 | ≤ 20 link‑preview URLs.                                                                                        |
| `location`                   | object                   | `{ lat, lng, placeName?, placeAddress? }`.                                                                     |
| `contact`                    | object                   | `{ name, phone, avatar?, userId? }`.                                                                           |
| `repliedToId`                | string                   | Reply target message id.                                                                                       |
| `receiverId`                 | string                   | Peer id (private).                                                                                             |
| `senderName`, `senderAvatar` | string                   | Denormalized, for instant fan‑out rendering.                                                                   |
| `clientTs`                   | number                   | Your compose time (epoch ms). Display hint only; never overrides `serverTs`.                                   |

**Ack (success):** `{ success:true, message:"...", data:{ messageId, conversationId, sequenceNumber, sentAt, alreadySent } }`
**Ack (error):** `{ success:false, error:"INVALID_PAYLOAD|SERVICE_ERROR|FORBIDDEN|NOT_FOUND|RATE_LIMITED|CONFLICT", retryable:boolean, message:"..." }`

> **Numeric coercion gotcha:** In the **ack**, `sentAt` / `sequenceNumber` may arrive as **strings** (gRPC int64). In the **`message:new` broadcast** they are **numbers**. Coerce defensively (`Number(x)`).

### 6.1 Text message

```js
chat.emit(
  "message:send",
  {
    conversationId,
    clientMessageId,
    conversationType: "private",
    contentType: "TEXT",
    contentText: "Hello!",
  },
  (ack) => {
    /* ack.data.messageId */
  }
);
```

**DB:** `content = { text:"Hello!", urls:[], files:[] }`, `messageType:"TEXT"`.
**History/broadcast:** `contentType:"TEXT"`, `content.text:"Hello!"`.

### 6.2 Image message

1. `POST /media/upload-url` `{ category:"CHAT_ATTACHMENT", contentType:"image/jpeg", contentLength }`
2. PUT bytes
3. send:

```js
contentType: "IMAGE",
files: [{ objectKey, name, size, mime:"image/jpeg", width, height, blurhash }]
```

**Render:** `msg.content.files[0].url` (resolved). Use `blurhash` for an instant placeholder while the image loads.

### 6.3 Video message

Same as image with `contentType:"VIDEO"`, `mime:"video/mp4"`, plus `durationMs`, `width`, `height`, optional `blurhash` (poster).
**Render:** `<video src={files[0].url}>`; show `durationMs` as the badge.

### 6.4 Audio message

`contentType:"AUDIO"`, `mime:"audio/mpeg"` (or `audio/ogg`/`audio/wav`), `durationMs`.

### 6.5 Voice note

`contentType:"VOICE"`, `mime:"audio/mp4"` (or `audio/ogg`), `durationMs`, and **`waveform: number[]`** (amplitude samples, ≤ 2048) for the waveform UI.

```js
contentType: "VOICE",
files: [{ objectKey, mime:"audio/mp4", durationMs:8500, waveform:[0.1,0.2,0.15,...] }]
```

### 6.6 Document / file message

`contentType:"DOCUMENT"`, `mime:"application/pdf"` (or doc/docx), `name`, `size`. No dimensions.
**Render:** file chip with `name` + human‑readable `size`; download via `files[0].url`.

### Per‑flow summary

| Flow     | API call         | `contentType` | `mime` examples                | Extra metadata                     |
| -------- | ---------------- | ------------- | ------------------------------ | ---------------------------------- |
| Text     | —                | `TEXT`        | —                              | —                                  |
| Image    | upload‑url + PUT | `IMAGE`       | `image/jpeg,png,webp,gif`      | `width,height,blurhash`            |
| Video    | upload‑url + PUT | `VIDEO`       | `video/mp4,quicktime`          | `durationMs,width,height,blurhash` |
| Audio    | upload‑url + PUT | `AUDIO`       | `audio/mpeg,ogg,wav`           | `durationMs`                       |
| Voice    | upload‑url + PUT | `VOICE`       | `audio/mp4,ogg`                | `durationMs,waveform[]`            |
| Document | upload‑url + PUT | `DOCUMENT`    | `application/pdf,msword,…docx` | `name,size`                        |

For **all** of the above: **Database storage** = raw `objectKey` in `content.files[]`; **Chat history response** = the same shape with `files[].url` resolved; **Frontend rendering** = read `files[0].url`.

### 6.7 System messages (group only)

Group lifecycle changes are persisted as messages with `contentType:"SYSTEM"`. Private chats have **no** system messages.

```json
{
  "contentType": "SYSTEM",
  "content": { "text": "Alice added Bob", "urls": [], "files": [] },
  "systemEvent": "MEMBER_ADDED",
  "systemData": {
    "actorId": "...",
    "actorName": "Alice",
    "targetUserId": "...",
    "targetName": "Bob"
  }
}
```

`systemEvent` values: `GROUP_CREATED`, `MEMBER_JOINED`, `MEMBER_LEFT`, `MEMBER_REMOVED`, `MEMBER_ADDED`, `ROOM_RENAMED`, `ROLE_CHANGED`, `AVATAR_CHANGED`, `DESCRIPTION_CHANGED`, `ADMIN_ASSIGNED`, `ADMIN_REMOVED`, `INVITE_LINK_CREATED`, `CALL_STARTED`, `CALL_ENDED`, `MESSAGE_PINNED`, `MESSAGE_UNPINNED`, `MESSAGES_ENCRYPTED`.

**Render:** prefer localizing from `systemEvent` + `systemData`; `content.text` is an English fallback.

### 7.4 Acknowledgement contract (all namespaces)

```jsonc

// error

```

| `error`           | `retryable` | Meaning                           |
| ----------------- | ----------- | --------------------------------- |
| `INVALID_PAYLOAD` | `false`     | Bad payload — fix and resend.     |
| `FORBIDDEN`       | `false`     | Not allowed (membership / role).  |
| `NOT_FOUND`       | `false`     | Target missing.                   |
| `CONFLICT`        | `false`     | Already applied / state conflict. |
| `SERVICE_ERROR`   | `true`      | Transient — retry with backoff.   |
| `RATE_LIMITED`    | `true`      | Throttled — retry after backoff.  |

Fire‑and‑forget events (`typing:*`, `presence:heartbeat`, `call:ice`) have **no ack** — never await them.

## 8. Community Chat Flow

Community chat is a **separate namespace** (`/community`) and uses a **flatter message shape** than private/group: a top‑level `message` string and an `attachments[]` array (not `content.files[]`). On the wire the message kind is `contentType` (UPPER); internally the store uses lower‑case `messageType`.

> Membership: browse rooms unauthenticated, but you must `POST /api/v1/chat/community/rooms/:roomId/join` (and `community:join` on the socket) to send/receive.

### 8.1 Community text message

```js
community.emit(
  "community:message:send",
  {
    communityId,
    clientMessageId: crypto.randomUUID(),
    contentType: "TEXT",
    message: "Hello community!",
  },
  (ack) => {
    /* … */
  }
);
```

### 8.2 Community image / video / file message

1. `POST /api/v1/media/upload-url` `{ category:"COMMUNITY_CHAT_ATTACHMENT", contentType, contentLength }`
2. PUT bytes
3. send with `media.files[]`:

```js
community.emit("community:message:send", {
  communityId,
  clientMessageId,
  contentType: "IMAGE",
  media: {
    files: [
      { objectKey, name, size, mime: "image/jpeg", width, height, blurhash },
    ],
  },
});
```

Video → `contentType:"VIDEO"`, `mime:"video/mp4"`, `durationMs`. Voice → `contentType:"VOICE"`, `waveform`. Document/file → `contentType:"CUSTOM"` with the file in `media.files[]`.

**On read** the broadcast/history exposes resolved URLs in `attachments[]` (each `{ objectKey, url, name, size, mime, width?, height?, durationMs?, blurhash?, waveform? }`). Render `attachments[i].url`.

## 9. Media URL Handling

A media file is represented two ways depending on direction:

```jsonc
// What you SEND in a message (reference the key):
{ "objectKey": "chat-uploads/<ownerId>/<fileId>.jpg" }

// What you RECEIVE on read (render the url; both are present):
{
  "objectKey": "chat-uploads/<ownerId>/<fileId>.jpg",   // stable identifier
  "url":       "https://minio.example.com/chat-uploads/.../<fileId>.jpg?X-Amz-Expires=3600&..."  // presigned, ~1h
}
```

For avatars / community images you receive a **`MediaObject`** descriptor (and a flat `*Url` legacy field):

```json
{
  "fileId": "a1b2c3d4",
  "objectKey": "avatars/<userId>/a1b2c3d4.webp",
  "fileName": null,
  "contentType": "image/webp",
  "size": null,
  "downloadUrl": "https://minio.example.com/avatars/.../a1b2c3d4.webp?X-Amz-Expires=3600&...",
  "downloadUrlExpiresIn": 3600,
  "uploadUrl": null,
  "uploadUrlExpiresIn": null
}
```

| Field                         | Frontend action                                                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------------ |
| **`objectKey`**               | **Store** it. Send it back when creating/updating (e.g. `avatarObjectKey`, `files[].objectKey`). |
| **`url`** / **`downloadUrl`** | **Display** it. Render directly. **Never persist** — it expires (~1 h).                          |
| **`uploadUrl`**               | Use **once** for the PUT, then discard. Never store.                                             |
| flat `avatarUrl` / `coverUrl` | Legacy mirror of `downloadUrl`; same render‑only rule.                                           |

**Why:** the DB stores raw `objectKey` and the backend re‑signs a fresh `url` on every read ("resolve‑on‑read"). If you cache a presigned URL it will 403 once it expires; re‑fetch the parent resource or call `POST /media/download-url` to mint a new one.

## 11. Realtime Flow

### 11.1 Sender side (step‑by‑step)

1. Connect `/chat` (or `/community`) with `auth.token`.
2. `conv:join { conversationId }` (idempotent; do it when opening a thread).
3. (Media only) `upload-url` → PUT bytes → keep `objectKey`.
4. Optimistically render a pending bubble keyed by your `clientMessageId`.
5. `message:send {…, clientMessageId}` with an ack callback.
6. On **ack success** → mark the bubble sent, store `messageId`/`sequenceNumber`. On **ack error** → if `retryable`, back off and resend the **same `clientMessageId`** (server dedupes via `alreadySent`); else surface the error.
7. You also receive your own `message:new` (multi‑device) — reconcile by `clientMessageId`, don't double‑insert.

### 11.2 Receiver side (step‑by‑step)

1. Connected and joined to the room (or in `user:<id>` for inbox bumps).
2. `message:new` → insert by `sequenceNumber` (monotonic per room); render `content.files[].url`.
3. Send `message:delivered { conversationId, upToMessageId }` (private) and, when the user views, `message:read { conversationId, upToMessageId }`.
4. React to `message:edited`, `message:delete`, `message:reaction`, `pin:updated`, `typing:*`, `presence:status`, `conv:updated` to keep the thread + list live.

### 11.3 Acknowledgements

Always pass the ack callback for non‑fire‑and‑forget events and branch on `success`. The `retryable` flag tells you whether a retry can succeed (see §7.4). Never retry `INVALID_PAYLOAD`/`FORBIDDEN`/`NOT_FOUND`/`CONFLICT`.

### 11.4 Failure handling & retry logic

| Situation                            | Handling                                                                                                                                                                                                                   |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ack `SERVICE_ERROR` / `RATE_LIMITED` | Exponential backoff; resend with the **same `clientMessageId`** (idempotent).                                                                                                                                              |
| Ack `CONFLICT` / `alreadySent:true`  | Treat as success — the message already landed.                                                                                                                                                                             |
| Socket disconnect / reconnect        | On reconnect, run **gap‑fill**: `chat:catchup { rooms:[{ roomId, sinceSeq }] }` (≤50 rooms) and `community:catchup` (≤10 rooms), using your highest stored `sequenceNumber`/`updatedAt` per room. Then resume live events. |
| `session:expired` received           | `auth:refresh { refreshToken }` (no reconnect) or reconnect with a fresh access token within the 60 s grace.                                                                                                               |
| Typing not received                  | Expected if it expired — server auto‑emits `typing:stop` after 6 s; also expire locally.                                                                                                                                   |

## 12. Common Frontend Mistakes

### ❌ Do **not**

- **Store presigned URLs** (`uploadUrl`, `downloadUrl`, `url`). They expire (~15 min upload / ~1 h download) and will 403.
- **Construct media URLs manually** from the bucket + key. Always use the server‑returned `url`/`downloadUrl`.
- **Use an `objectKey` as an `<img src>`.** A key is not a URL.
- **Hardcode socket event names** with guesses. Use exactly the strings in §7 (e.g. it's `message:new`, not `message:received`).
- **Send media bytes through the gateway or socket.** PUT directly to `uploadUrl`.
- **Await fire‑and‑forget events** (`typing:*`, `presence:heartbeat`, `call:ice`) — they have no ack.
- **Double‑insert your own message** — you receive your own `message:new`; reconcile by `clientMessageId`.
- **Merge** community `pinnedIds[]` — it's the **complete** set; replace your local list.

### ✅ Always

- **Store the `objectKey`** and send it back (`files[].objectKey`, `avatarObjectKey`).
- **Render the resolved `url`/`downloadUrl`** returned on read.
- **Store `messageId` and per‑room `sequenceNumber`** for ordering + reconnect gap‑fill.
- **Send a `clientMessageId`** and handle acks (success / `retryable` error).
- **Coerce numeric timestamps** (`Number(sentAt)`) — they're strings in acks, numbers in broadcasts.
- **Send the `headers` object** from the upload‑url response on your PUT.

## 13. Troubleshooting

| Symptom                             | Likely cause                                      | Fix                                                                                       |
| ----------------------------------- | ------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| **Upload URL expired / PUT 403**    | `uploadUrl` older than `uploadExpiresIn` (~900 s) | Request a fresh `upload-url` and PUT again. Don't cache upload URLs.                      |
| **PUT 403 / signature mismatch**    | Extra/missing headers on PUT                      | Send **exactly** the returned `headers` (`Content-Type` only). No `Authorization`.        |
| **415 on upload‑url**               | `contentType` not allowed for `category`          | Check the allow‑list in §4.1 (avatars = image only; chat = image/video/audio/docs).       |
| **400 `UPLOAD_FILE_TOO_LARGE`**     | `contentLength` > category max                    | Compress / chunk; avatars ≤ 5 MB, chat ≤ 100 MB.                                          |
| **403 on download‑url**             | `CHAT_ATTACHMENT` key not owned by you            | Use the correct category; community/group keys are prefix‑checked only.                   |
| **Socket won't connect**            | Missing/expired JWT, wrong path/namespace         | Pass `auth:{ token }`, `path:"/socket.io/"`, connect to `/chat`\|`/community`\|`/notify`. |
| **Message not received**            | Not joined to the room                            | Emit `conv:join` / `community:join` before expecting `message:new`.                       |
| **Missed messages after reconnect** | No gap‑fill                                       | Run `chat:catchup` / `community:catchup` with your last `sequenceNumber`.                 |
| **Media not loading after a while** | Cached an expired presigned `url`                 | Re‑fetch history or call `POST /media/download-url` for a fresh URL.                      |
| **"Invalid media URL"**             | Rendered an `objectKey` instead of `url`          | Render `files[i].url` / `media.downloadUrl`, not the key.                                 |
| **Duplicate bubbles**               | Inserting your own `message:new` again            | Reconcile by `clientMessageId`; treat `alreadySent` as success.                           |
| **Timestamps look wrong**           | String vs number from gRPC                        | `Number(sentAt)` in acks; broadcasts are already numbers.                                 |
| **Ack never fires**                 | Fire‑and‑forget event, or no ack callback passed  | `typing:*`/`presence:heartbeat`/`call:ice` have no ack; pass a callback for the rest.     |
| **503 on `/users/uploads/url`**     | `media-service` down / `MEDIA_SERVICE_URL` unset  | Use `/api/v1/media/upload-url` directly; ensure media‑service is running.                 |

## 16. Swagger Mismatch & Missing‑Docs Report

Findings from comparing the OpenAPI document against the actual implementation. **Where they disagree, the code (this guide) wins.**

### 16.1 Implemented but **not documented** in Swagger

1. **`DELETE /api/v1/media/uploads/:objectKey`** (cancel upload) — fully implemented in `media-service` (`media.controller.ts`/`media.routes.ts`) but absent from `media.paths.ts`. _(Known internally as gap R‑08.)_
2. **Private/Group pin & unpin actions** — `POST|DELETE /chat/{private/rooms/:roomId,groups/:roomId}/messages/:messageId/pin` are implemented; OpenAPI documents the **list** path (`…/pins`) but not the pin/unpin action paths.
3. **Private/Group archive & unarchive** — `PATCH …/rooms/:roomId/archive|unarchive` (private) and `PATCH /chat/groups/:roomId/archive|unarchive` are implemented but not present as OpenAPI path keys.
4. **Private mute/unmute** are documented; **edit** (`PATCH /chat/private/messages/:messageId`) shares a path key with delete — verify the `PATCH` operation is described, not only `DELETE`.

### 16.2 Response in docs implies a feature with **no setter**

5. **Community cover image** — `CommunityData` exposes `coverUrl` + `cover` (`MediaObject`), but neither `CreateCommunityRequest` nor `UpdateCommunityRequest` accepts a `coverObjectKey` (confirmed in `community.validator.ts`). Cover images **cannot currently be set via REST**. Either add `coverObjectKey` support or stop advertising cover in the response.

### 16.3 Timestamp representation is inconsistent in docs

6. `ChatCommunityMessage` documents `createdAt`/`editedAt` as **ISO‑8601 strings**, but `updatedAt`, `readBy[].readAt`, `deliveredTo[].deliveredAt` as **epoch‑ms integers**. The wire/serializer convention (and `ApiResponse.toJSON` Date→epoch‑ms) is **epoch‑ms**; OpenAPI strings are stale in places. On the wire, treat `serverTs`/`sentAt`/`editedAt`/`updatedAt` as **epoch‑ms numbers**; `createdAt` may appear as an ISO string in some REST responses — parse defensively.

### 16.4 Request body under‑documented

7. **`community:message:send` / community message creation** — the rich body (`contentType`, `message`, `media.files[]`, `location`, `contact`, `sticker`, `parentMessageId`) is not fully captured in OpenAPI request schemas. This guide (§8) is the authoritative shape.

### 16.5 Docs lag behind socket capabilities

8. `docs/SOCKET_EVENTS.md` marks **friend** and **community moderation** flows as "REST‑only / deferred", but the `/chat` and `/community` namespaces **do** implement them as socket events (`friend.request/accept/reject/remove/cancel_request`; `community.member.kick/ban/unban`, `community.admin.transfer`, `community.member.role_change`, `community.report.create`, `community.delete`). `auth:refresh` and `session:expired` are likewise implemented though docs label them V2/deferred. §7 reflects the real, working events.

### 16.6 Things that are **consistent** (verified, no action needed)

- Media `category` enum (7 values) matches between OpenAPI, gRPC contract, and `media-service`.
- `contentType` is the single UPPER‑case message‑kind field across REST + socket; internal `messageType` never leaks.
- No raw object keys leak on read — all media is resolve‑on‑read to presigned URLs (chat `content.files[].url`, community `attachments[].url`, avatars `downloadUrl`).
- Chat REST path keys in OpenAPI (`/chat/private/...`, `/chat/groups/...`, `/chat/community/...`) match the actual gateway routes (server base prepends `/api/v1`).
