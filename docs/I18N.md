# Internationalization (i18n)

How AIMess renders user-facing text in the reader's own language, everywhere it
originates: REST responses, socket acks, socket events, SYSTEM chat lines, push
notifications and the Notification Center.

**One catalog, one `t()`, one locale resolution chain.** There is no second
translation mechanism, and adding one is a bug.

---

## Supported languages

| Code | Language   |
| ---- | ---------- |
| `en` | English    |
| `vi` | Vietnamese |
| `th` | Thai       |

Declared once, in `packages/constants/src/locale.ts`:

```ts
export const SUPPORTED_LOCALES = ["vi", "en", "th"] as const;
export type SupportedLocale = (typeof SUPPORTED_LOCALES)[number];
```

`DEFAULT_LOCALE` is **English in dev/test, Vietnamese in production** (unchanged
behavior). ISO 639-1 codes only — never `vn`, `viet`, `thai-th`.

`STORED_TEXT_LOCALE` is a separate constant, permanently `"en"`. See
[Stored SYSTEM text](#stored-system-text-and-historical-messages).

---

## How language is resolved

```
x-lang header            (explicit, wins)
      ↓
Accept-Language header   (browser/client default)
      ↓
DEFAULT_LOCALE           (vi in production, en elsewhere)
```

`resolveLocale(acceptLanguage, xLang)` in `packages/constants/src/i18n.ts` owns
this and normalizes prefixes (`th-TH` → `th`, `en-GB` → `en`).

**Where each surface gets it:**

| Surface                    | Source                                                                             |
| -------------------------- | ---------------------------------------------------------------------------------- |
| REST (every service)       | `localeMiddleware` → `req.locale`                                                  |
| Socket.IO (all namespaces) | handshake `x-lang` / `Accept-Language` → `socket.data.locale`                      |
| Internal gRPC              | `x-lang` call metadata, set from the ambient context, read in `withServiceAuth`    |
| Push / Notification Center | the **recipient's** `AppSettings.language`, via the cached user-settings gRPC call |

The user's stored `AppSettings.language` (`en` \| `vi` \| `th`, Settings →
General) is deliberately **not** consulted per REST request — clients send
`x-lang`, and a per-request preference lookup would add a gRPC round-trip to
every call. It is authoritative exactly where there is no request to read a
header from: server-initiated notifications.

### The ambient locale context

The locale enters at one edge but is needed deep inside a service, so it rides
an `AsyncLocalStorage` (`packages/constants/src/locale-context.ts`) instead of a
`locale` parameter threaded through every signature:

```ts
runWithLocale(locale, () => {
  /* everything in here sees it */
});
currentLocale(); // → SupportedLocale, DEFAULT_LOCALE outside a request
```

Set by `localeMiddleware` (HTTP), `scopeSocketLocale` (each socket packet), and
`withServiceAuth` (each inbound gRPC call). Egress gRPC calls attach
`currentLocale()` as `x-lang` metadata automatically, so the chain survives
gateway → service hops with **no proto change**.

An explicit `locale` argument always wins where one exists; the context is the
fallback for code that cannot reasonably be handed one.

## Translation key convention

Keys are stable `UPPER_SNAKE_CASE` identifiers, grouped by domain file under
`packages/constants/src/messages/`:

| File                       | Prefix               | Contents                                |
| -------------------------- | -------------------- | --------------------------------------- |
| `auth.messages.ts`         | `AUTH_*`             | register / login / session / OTP        |
| `user.messages.ts`         | `USER_*`, `FRIEND_*` | profile, settings, friendships          |
| `chat.messages.ts`         | `CHAT_*`             | private + group REST                    |
| `community.messages.ts`    | `COMMUNITY_*`        | community REST                          |
| `socket.messages.ts`       | `SOCKET_*`           | socket ack copy                         |
| `media.messages.ts`        | `MEDIA_*`            | media/upload errors                     |
| `stream.messages.ts`       | `STREAM_*`           | livestream                              |
| `admin.messages.ts`        | `ADMIN_*`            | backoffice                              |
| `system.messages.ts`       | `SYS_*`              | SYSTEM chat lines, call rows, durations |
| `notification.messages.ts` | `NOTIF_*`            | push + Notification Center copy         |
| `common.messages.ts`       | —                    | shared across services                  |

Never use English text as a key:

```ts
t("Member removed from group"); // ✗
t("SYS_GROUP_MEMBER_REMOVED", locale, { actor, target }); // ✓
```

Each entry carries all three languages, and the type enforces it:

```ts
SYS_GROUP_MEMBER_REMOVED: {
  vi: "{{actor}} đã xóa {{target}}",
  en: "{{actor}} removed {{target}}",
  th: "{{actor}}นำ{{target}}ออกจากกลุ่ม",
},
```

`LocalizedText = Record<SupportedLocale, string>`, so **a key missing `th` is a
compile error**, not a runtime fallback.

## Using translations

### Backend

```ts
import { t } from "@aimess/constants";

t("CHAT_MESSAGE_SENT", req.locale);
t("SYS_GROUP_MEMBER_REMOVED", locale, { actor: "Alex", target: "Jim" });
```

**Interpolation.** Never concatenate around a translation — word order differs
per language. Placeholders are `{{name}}`; an unmatched placeholder is left
visible (`{{who}}`) rather than blanked, so a missing param is obvious in dev
instead of silently producing `"  was removed"`.

**Pluralization.** The catalog is flat strings, so plural-sensitive text uses
paired `_ONE` / `_OTHER` keys selected by the caller:

```ts
t(count === 1 ? "SYS_DURATION_DAY_ONE" : "SYS_DURATION_DAY_OTHER", locale, {
  count,
});
```

`vi` and `th` carry the same string in both slots — neither marks plural on the
noun. That is correct, not a copy-paste slip, and the catalog validator has an
allowlist so it is not flagged as untranslated.

**Dates/numbers.** Locale-aware via `Intl` (`en-US` / `vi-VN` / `th-TH`). The one
exception is the mute-expiry stamp inside a SYSTEM line, which keeps
`toUTCString()` for English because that exact string is baked into historical
rows.

### REST responses

Response shape is unchanged; only the text is localized.

```ts
res
  .status(HTTP_STATUS.OK)
  .json(new ApiResponse(data, t("USER_SETTINGS_UPDATED", req.locale)));
```

Errors carry a **stable machine code plus a localized sentence**:

```json
{
  "success": false,
  "error": {
    "statusCode": 403,
    "code": "FRIEND_REQUEST_NOT_ALLOWED",
    "message": "<localized>"
  }
}
```

Throw with the key; the service's `errorHandler` localizes it against
`req.locale`:

```ts
throw new ForbiddenError("FRIEND_REQUEST_NOT_ALLOWED");
```

Clients must branch on `error.code`, never on `error.message`.

### Socket.IO

Acks already carry a localized, display-ready `message` — pass a key plus the
connection locale, never a raw string:

```ts
ackOk(callback, "SOCKET_MESSAGE_SENT", socket.data.locale, data);
```

### Frontend

The web/mobile clients live in their own repositories. They must:

1. send `x-lang: en|vi|th` on every REST call **and** in the socket handshake;
2. render `message` from the response as-is (it is already localized);
3. branch on `error.code`, never on `error.message`;
4. re-send the handshake locale after the user changes language (see
   [Changing language](#changing-language-at-runtime)).

## System messages

SYSTEM chat lines ("Alex removed Jim", "You are now the group admin") are built
by four functions in `@aimess/constants`:

| Function                           | Covers                              |
| ---------------------------------- | ----------------------------------- |
| `buildGroupSystemFallbackText`     | group lifecycle                     |
| `buildPrivateSystemFallbackText`   | 1:1 friendship / auto-delete / pins |
| `buildCommunitySystemFallbackText` | community lifecycle                 |
| `buildCallTimelineText`            | call rows (DM and group)            |

Each takes an optional trailing `locale` that **defaults to
`STORED_TEXT_LOCALE`** (English). Two rules follow from that:

- **Write paths never pass a locale.** The sentence persisted on the message row
  stays English forever.
- **Read paths always pass the viewer's locale.** They re-render from the stored
  `systemEvent` + `systemData` (or `systemMessageType` + `systemMetadata`), so
  the reader sees their own language.

Per-viewer forms come from the same call: when `viewerUserId` matches the actor
or target, the builder returns the first-person `_SELF` key.

### Stored SYSTEM text and historical messages

Nothing is migrated and nothing is rewritten in the database. The stored English
sentence is only a fallback; every read path rebuilds. That means editing a
translation instantly changes **historical** rows too, in every language,
including English.

## Per-recipient delivery

> One event. Three recipients. Three languages. No publisher awareness.

### Socket fan-out

`emitPersonalizedSender` (api-gateway) is the only place a room broadcast visits
sockets one at a time, so it is where locale lands:

```ts
for (const socket of await namespace.in(channel).fetchSockets()) {
  const locale = socket.data.locale ?? DEFAULT_LOCALE;
  socket.emit(event, personalizeFn(payload, socket.data.userId, locale));
}
```

A `personalizeFn` has the signature `(data, viewerUserId, locale) => data`. The
"you are the sender" swap is localized the same way (`t("SYS_SENDER_YOU", locale)`),
so a Vietnamese reader sees `Bạn`, not `You`.

Covered by `apps/api-gateway/tests/sockets/per-recipient-locale.test.ts`.

### Push / Notification Center

Consumers never render copy. They hand `pushToUser` a **thunk**:

```ts
await pushToUser({
  userId: p.addresseeId,
  category: "friendRequestEnabled",
  type,
  copy: friendCopy.requested(p.requesterName), // (locale) => NotificationCopy
});
```

`pushToUser` resolves the recipient's language (`getUserLocale`, backed by the
Redis-cached user-settings gRPC call) and only then invokes the thunk. The same
builder therefore produces a different sentence per recipient. User-facing text
inside the FCM `data` map (e.g. the friend-request `resolution` line) uses
`localizedData: (locale) => ({ … })` for the same reason.

`AppSettings.language` reaches notifications-service as an **additive**
`language` field on the existing `user.NotificationSettings` gRPC message — no
new RPC, no breaking proto change, and it is invalidated by the existing
`user.settings_updated` cache-bust consumer.

Covered by `apps/notifications-service/tests/services/push-recipient-locale.test.ts`.

## Changing language at runtime

`PATCH /api/v1/users/settings/me` with `{ "app": { "language": "th" } }`:

1. persists to `AppSettings.language`;
2. publishes `user.settings_updated` → notifications-service busts its cached
   settings, so the **next** push is Thai;
3. emits `settings:updated` to the user's other devices with the full new
   settings DTO.

No logout, no reconnect required. Already-delivered messages are not rewritten
(they were rendered for the locale in force at delivery). New REST calls follow
the new `x-lang` the client sends; new socket events follow the locale of the
next handshake, so a client that wants immediate socket-side effect should
reconnect after changing language.

Language is **account-level**, not device-level: every device of the same
account gets the same push language. A device may still request a different
`x-lang` for its own REST/socket traffic.

## Adding a translation key

1. Pick the domain file under `packages/constants/src/messages/`.
2. Add the entry with **all three** languages (TypeScript will not compile
   otherwise), using `{{placeholders}}` rather than concatenation.
3. Use it: `t("MY_NEW_KEY", locale, { … })`.
4. `pnpm --filter @aimess/constants build` — `packages/*` are **not** watched by
   `pnpm dev`, so a stale `dist` is the usual cause of "my key isn't there".
5. `pnpm validate:i18n`.

## Adding a language

1. Add the code to `SUPPORTED_LOCALES` in `packages/constants/src/locale.ts`.
2. Add a prefix branch in `normalizeLocale` (`packages/constants/src/i18n.ts`).
3. Compile — every catalog entry now fails until the new language is filled in.
   That list **is** the work queue.
4. Add the `Intl` tag in the two `INTL_LOCALE` maps
   (`community/system-message-text.ts`, `notifications-service/lib/notification-copy.ts`).
5. Extend the `x-lang` enum in `apps/api-gateway/src/docs/openapi/components/parameters.ts`
   and the `languageSchema` in `apps/user-service/src/api/validators/settings.validator.ts`.
6. `pnpm validate:i18n && pnpm test:all`.

## Validation

Key parity is a **compile-time** guarantee. Everything the type cannot see is
checked by a validator that runs two ways:

```bash
pnpm validate:i18n
```

and as a test (`apps/api-gateway/tests/i18n/catalog-parity.test.ts`), so
`pnpm test:all` fails on a bad catalog. It rejects:

- blank / whitespace-only values;
- placeholder drift (`{{name}}` in `en` but missing in `vi`/`th`, which would
  silently drop the value in that language only);
- a non-English value byte-identical to English (untranslated copy-paste), with a
  small allowlist for keys that are pure structure;
- any catalog key that resolves to its own name.

---

## Fallback

```
requested locale → entry[locale] → entry[DEFAULT_LOCALE] → entry.en → key
```

The last step is unreachable for catalog keys — the parity test asserts no key
resolves to its own name in any locale, so **a raw key is never shown to a
user**. In development a missing key surfaces immediately as a failing test
rather than a silent English fallback.

## What is deliberately NOT translated

| Category                | Example                                                  | Why                                                           |
| ----------------------- | -------------------------------------------------------- | ------------------------------------------------------------- |
| Operational logs        | `logger.error("Failed to connect to Redis")`             | read by operators, not users                                  |
| Internal error text     | `throw new Error("Failed to allocate invite-link code")` | never reaches a client; surfaces as the localized generic 500 |
| Socket handshake errors | `new Error("Authentication required")`                   | clients branch on these strings — they are codes, not copy    |
| User-authored content   | announcement title/body, a moderator's warning note      | written by a human for a specific audience                    |
| Technical identifiers   | enum values, event names, `objectKey`, API paths         | contract, not copy                                            |
| OpenAPI examples        | `message: "Welcome everyone!"`                           | documentation fixtures                                        |

## Known limitations

**1. Conversation / community LIST previews for SYSTEM rows are English.**

The list preview does not come from the message document; it comes from the
denormalized `lastMessagePreview` / `lastMessage` JSON blob on the room, which
stores the baked English sentence and does **not** carry `systemEvent` /
`systemData`. Both the REST inbox and the live `conv:updated` / `community:updated`
bump therefore show the English line, even though opening the conversation shows
the same event translated. Regular (non-SYSTEM) previews are user content and are
unaffected.

_Upgrade path:_ add `systemEvent` + `systemData` to that blob at write time (the
columns are free-form `Json?`, so no migration), then rebuild the preview in the
inbox serializer with `currentLocale()` and add a `conv:updated` /
`community:updated` `personalizeFn` in the gateway — the exact pattern
`message:new` already uses. Do both together: localizing only the live bump would
make the list flip language on refresh.

**2. Zod field-level validation detail is English.**

`validateBody`/`validateQuery`/`validateParams` return the merged Zod issue text
as `message` (e.g. `"Version must be major.minor.patch (e.g. 1.0.5)"`). These are
per-field technical details with no stable key, and the response predates the
`{ code, message }` envelope. The generic failure (`VALIDATION_FAILED`) and every
business error ARE localized and carry a stable `code`.

_Upgrade path:_ give each schema a message key instead of a sentence and localize
in the middleware — but only alongside a client migration, since the current
`message` is what clients display today.
