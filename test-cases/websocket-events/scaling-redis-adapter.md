# WebSocket — Horizontal Scaling & Redis Adapter Fan-out

Backend services never hold sockets — they `publish` `{ event, data }` to a Redis
channel and the gateway re-emits to the matching room. The Socket.IO **Redis
adapter** (`@socket.io/redis-adapter`) lets multiple gateway instances share rooms
so a `chat.to(room).emit(...)` on instance 1 reaches sockets on instance 2. Each
namespace uses a **dedicated** Redis subscriber client (ioredis cannot mix
`psubscribe` and `subscribe` on one connection, and sharing a psubscribe client
cross-fires pmessage handlers). The adapter pub/sub is separate from the
app-level channel subscribers.

**Source:** `apps/api-gateway/src/sockets/index.ts`,
`apps/api-gateway/src/sockets/redis.ts`, the per-namespace `psubscribe`/`subscribe`
blocks, `docs/SOCKET_EVENTS.md` §1 (intro), §5, §6.

### TC-WS-230 — Cross-instance fan-out via Redis adapter

| Field                     | Value                                                                                                                                                                                                                         |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Feature/Module**        | WebSocket / Scaling                                                                                                                                                                                                           |
| **API/Event Name**        | adapter broadcast (`io.adapter(createAdapter(pub,sub))`)                                                                                                                                                                      |
| **Test Scenario**         | Happy path — sender on instance-1, recipient on instance-2 of the same conversation receives `message:new`                                                                                                                    |
| **Category**              | Concurrency                                                                                                                                                                                                                   |
| **Priority**              | High                                                                                                                                                                                                                          |
| **Preconditions**         | Two gateway instances behind a LB sharing the same Redis; A→instance-1, B→instance-2; both in `conv:<id>`                                                                                                                     |
| **Request Payload**       | A emits `message:send`                                                                                                                                                                                                        |
| **Expected Response**     | Ack to A on instance-1                                                                                                                                                                                                        |
| **Expected DB Changes**   | Message persisted once                                                                                                                                                                                                        |
| **Expected Socket/Event** | chat-service publishes `message:new` to `conv:<id>`; whichever gateway instance's app-level `conv:*` subscriber receives it calls `chat.to(conv:<id>).emit(...)`, and the Redis **adapter** fans that emit to B on instance-2 |
| **Notes**                 | Two layers of Redis: (1) app channel `conv:*` carrying service→gateway events, (2) the adapter carrying gateway→gateway room broadcasts. Both must be on the same Redis.                                                      |

### TC-WS-231 — No duplicate emit when multiple instances subscribe conv:\*

| Field                     | Value                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Feature/Module**        | WebSocket / Scaling                                                                                                                                                                                                                                                                                                                                                             |
| **API/Event Name**        | Redis `pmessage` (`conv:*`)                                                                                                                                                                                                                                                                                                                                                     |
| **Test Scenario**         | Concurrency — every gateway instance psubscribes `conv:*`; ensure a recipient doesn't get the event twice                                                                                                                                                                                                                                                                       |
| **Category**              | Concurrency                                                                                                                                                                                                                                                                                                                                                                     |
| **Priority**              | High                                                                                                                                                                                                                                                                                                                                                                            |
| **Preconditions**         | 2+ instances, each with a `conv:*` subscriber; recipient B on instance-2                                                                                                                                                                                                                                                                                                        |
| **Request Payload**       | service publishes one `message:new` to `conv:<id>`                                                                                                                                                                                                                                                                                                                              |
| **Expected Response**     | n/a                                                                                                                                                                                                                                                                                                                                                                             |
| **Expected DB Changes**   | None                                                                                                                                                                                                                                                                                                                                                                            |
| **Expected Socket/Event** | **Risk:** both instances receive the `pmessage` and each calls `chat.to(conv:<id>).emit(...)`. With the Redis adapter, an instance broadcasting to a room emits to its **own** local sockets AND requests other instances to emit to theirs → B could receive the same `message:new` **twice** (once from instance-1's adapter fan-out, once from instance-2's local handling). |
| **Notes**                 | **POTENTIAL DUPLICATE-DELIVERY GAP under multi-instance.** Verify in a real 2-instance setup. Mitigations: have only one logical consumer per channel, or make events idempotent client-side (most are keyed by `messageId`/`sequenceNumber`). Single-instance deployments are unaffected. Flag for review.                                                                     |

### TC-WS-232 — Namespace subscriber isolation (no pmessage cross-firing)

| Field                     | Value                                                                                                                                                                                    |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Feature/Module**        | WebSocket / Scaling                                                                                                                                                                      |
| **API/Event Name**        | per-namespace dedicated sub client                                                                                                                                                       |
| **Test Scenario**         | Edge — `/chat`, `/community`, `/notify` each use their own sub client; a `community:*` message must not fire the `/chat` handler                                                         |
| **Category**              | Edge Case                                                                                                                                                                                |
| **Priority**              | High                                                                                                                                                                                     |
| **Preconditions**         | All three namespaces registered                                                                                                                                                          |
| **Request Payload**       | publish to `community:<id>`                                                                                                                                                              |
| **Expected Response**     | n/a                                                                                                                                                                                      |
| **Expected DB Changes**   | None                                                                                                                                                                                     |
| **Expected Socket/Event** | Only `/community`'s subscriber re-emits; `/chat`'s pmessage handler guards with `allowedPatterns.includes(pattern)` and `/notify` uses exact `subscribe` ignoring non-`notify:` channels |
| **Notes**                 | Dedicated clients prevent the documented cross-firing bug (mixing psubscribe/subscribe). `/chat` also pattern-guards defensively.                                                        |

| **API/Event Name**        | Redis connection error handling                                                                                                                                                                                       |

| **Category**              | Error Handling                                                                                                                                                                                                        |

| **Request Payload**       | n/a                                                                                                                                                                                                                   |
| **Expected Response**     | n/a                                                                                                                                                                                                                   |
| **Expected DB Changes**   | None                                                                                                                                                                                                                  |
| **Expected Socket/Event** | `error` handlers swallow until reconnect; `maxRetriesPerRequest:null` keeps retrying; while down, cross-instance fan-out and channel re-emits pause — clients recover missed messages via `chat:catchup` on reconnect |

### TC-WS-235 — Sticky-session not required (stateless handshake)

| Field                     | Value                                                                                                                                                                                                               |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Feature/Module**        | WebSocket / Scaling                                                                                                                                                                                                 |
| **API/Event Name**        | LB routing                                                                                                                                                                                                          |
| **Test Scenario**         | Edge — websocket transport pinned per-connection; auth is per-handshake JWT (no server session affinity)                                                                                                            |
| **Category**              | Edge Case                                                                                                                                                                                                           |
| **Priority**              | Low                                                                                                                                                                                                                 |
| **Preconditions**         | `transports:["websocket"]` recommended client config                                                                                                                                                                |
| **Request Payload**       | n/a                                                                                                                                                                                                                 |
| **Expected Response**     | n/a                                                                                                                                                                                                                 |
| **Expected DB Changes**   | None                                                                                                                                                                                                                |
| **Expected Socket/Event** | A single websocket stays on one instance; rooms work across instances via the adapter, so no sticky sessions are needed for fan-out. Polling-fallback transport would need stickiness.                              |
| **Notes**                 | If clients use the polling fallback the LB must be sticky; with pure websocket it is not required. `connectionStateRecovery` reconnect may land on a different instance — recovery state is stored via the adapter. |

### TC-WS-236 — call:ice fan-out correctness across instances

| Field                     | Value                                                                                                                                                                                                                                                                                                   |

| **API/Event Name**        | `call:ice` cross-instance                                                                                                                                                                                                                                                                               |

| **Preconditions**         | Caller→instance-1, callee→instance-2, both in `call:<callId>`                                                                                                                                                                                                                                           |
